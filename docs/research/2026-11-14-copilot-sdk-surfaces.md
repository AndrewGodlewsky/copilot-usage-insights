# Copilot desktop SDK data surfaces for efficiency analysis

Research date: November 14, 2026. Repository baseline: `e0824ebe407140aa3d4519f8b5bb13fbb3af46bd`. This is a contract audit, not a report of newly collected user activity or shipped functionality.

The most useful additional surface is **current context attribution**. The installed desktop SDK exposes token occupancy by skill, subagent, MCP server, tool, and plugin, alongside aggregate context categories and the largest individual messages. This can answer “what occupies this session’s context now?” It cannot answer “how many tokens did this skill consume over the last month?” or “was this tool useful?” The next useful historical candidates are turn/agent joins, compaction results, metered tool operations, and error/permission timing, subject to measured persisted coverage.

The existing joined extension has a declared route to these current-session methods through `session.rpc`. It does **not** expose the general client’s server RPC object for reading arbitrary saved sessions. No host RPC, model inference, permission action, configuration change, user log, or user database was invoked/read for this audit. Only this research file was written.

## Evidence and access boundaries

The inspected SDK root is `%LOCALAPPDATA%/Programs/GitHub Copilot/copilot-sdk`. Its `cliVersion.d.ts:1` identifies bundled runtime **`1.0.106-8.unstable.r43360710077.gff3c476`**. This is a runtime build identifier, not a claim about an npm SDK package version. Source identifiers such as **R:41238** below refer to the file and line in the provenance table at the end.

- **Declared and locally available:** the installed `.d.ts` files declare a method or field. This establishes the host-bundled SDK surface, not successful authorization or a non-null result from the running desktop host.
- **Documented online:** official GitHub source/docs corroborate semantics. Online `main` moves independently of the installed runtime; its extra fields are not automatically installed capabilities.
- **Observed user data:** deliberately outside this audit. The companion stored-data audit determines which events/fields actually occur in desktop journals and databases.

The [extension entry point](../../src/extension.mjs) imports `joinSession` from the host’s extension SDK. Local `extension.d.ts:59` returns `Promise<CopilotSession>`; `session.d.ts:101` exposes `createSessionRpc`, and `session.d.ts:209,232` declares event subscriptions. Thus the session-scoped APIs below are reachable through the existing architecture without creating another session. Feature checks, timeouts, null handling, and isolated failures remain necessary. The [existing inventory reader](../../src/node/integrations.mjs) already applies that pattern to MCP and plugins. Its current scope is these two inventories; the other methods below are research candidates.

Static inspection of the installed **implementation** confirms this route: `extension.js:11421` constructs `session.rpc` with `createSessionRpc`, and `extension.js:8845,8853` forwards the two context-attribution queries over the existing connection with the hosting `sessionId`. The SDK module was read as text, never imported/executed for this audit. This verifies that the wrappers exist; host acceptance and populated responses remain untested.

| `session.rpc.eventLog.read(...)` / `tail()` | Declared, R:41483,41489 | Bounded hosting-session reads, with event-type, agent, direction, and ephemeral filters. `history` follows original journals; `replay` describes the active replay head. R:14479 |
| `client.rpc.sessions.readPersistedEvents(...)` | **General SDK only**, absent from this joined session’s public object | Passive arbitrary local-session journal paging without activation/resume. Declared on `createServerRpc`, R:39071; the extension exposes `createSessionRpc`, R:39265. Do not invent `session.rpc.sessions` or reach through private connection fields. |
| `client.listSessions()`, server account quota/model APIs | General client/server surface | Useful outside the current extension boundary. For bounded history reads, use the declared `types`, `max` (1–1000), `agentScope`, `direction`, and `includeEphemeral:false` options. Follow `hasMore`, not the number of returned events. An expired active-session cursor can overlap prior pages; deduplicate/reset deliberately. The server’s persisted reader instead pins a journal generation, uses sequential single-use cursors, and returns an empty terminal expired page rather than silently changing snapshots. Neither route recreates already-lost ephemeral events. R:14479,14552,31483,39065.

The local event file contains 150 event interfaces with a type discriminator; 77 require `ephemeral:true`. The remaining interfaces permit an optional ephemeral flag, so an event’s actual envelope still governs retention. Official [streaming-event documentation](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/streaming-events) distinguishes transient delivery from persisted/replayed history. A documented event type is not proof that a particular desktop release saved it. Conversely, the desktop may independently persist sampled values from transient events in its own tables; the SDK retention contract does not rule out those separate stores.

## Current context can be attributed without collecting message bodies

These are experimental session metadata reads, not inference-starting methods. Their contracts return existing context or an uninitialized result; this audit did not call them or force initialization. R:41232–41246. Official [generated Node RPC source](https://raw.githubusercontent.com/github/copilot-sdk/cf045793958ce674259c557f7769788f94ee20c9/nodejs/src/generated/rpc.ts) and [GitHub’s Java metadata API](https://github.github.com/copilot-sdk-java/1.0.29-preview.9/apidocs/com.github.copilot.java/com/github/copilot/generated/rpc/SessionMetadataApi.html) corroborate the surface.

| Method / schema | Useful fields | Meaning and limitations |
| --- | --- | --- |
| `metadata.contextInfo({promptTokenLimit:0, outputTokenLimit:0})`; `SessionContextInfo` | `modelName`, `provider`, `systemTokens`, `conversationTokens`, `toolDefinitionsTokens`, `mcpToolsTokens`, `totalTokens`, `promptTokenLimit`, `limit`, `bufferTokens`, `compactionThreshold` | Tokenization of current resident context. MCP definitions are a subset of all tool definitions; deferred definitions are excluded. Zero limits request session defaults. The display allowance `limit` and effective input budget `promptTokenLimit` differ because of output reservation. Missing/null `contextInfo` means uninitialized, not empty. R:4485,20980,21005 |
| `metadata.getContextAttribution()`; `SessionContextAttribution` | `totalTokens`, `modelId`, `modelSource`, budget fields, `categories`, `entries`, `compactions.count` | Current per-source attribution and number of successful compactions. Optional/null `contextAttribution` until system prompt/tool metadata initialize. R:4375,20937,41238 |
| `metadata.getContextHeaviestMessages({limit})`; `ContextHeaviestMessage` | Result `totalTokens`; each message’s `id`, `label`, `role`, `tokens` | Largest currently resident messages, descending by tokens. **No message body field** in this schema. Empty list when uninitialized; do not interpret that alone as “all messages are small.” R:13335,20950,20963,41246 |

Attribution categories are `systemPrompt`, `customInstructions`, `systemTools`, `mcpTools`, `messages`, `freeSpace`, and `buffer`. Free space and buffer describe capacity rather than occupied tokens; adding every category does not yield `totalTokens`. Each source entry has `kind`, stable-in-snapshot `id`, presentation-only `label`, `tokens`, optional `parentId`, and optional string-valued `attributes`. Known kinds are `skill`, `subagent`, `mcpServer`, `tool`, `system`, `toolDefinition`, and `plugin`; future kinds must remain displayable. Attributes can include `messageCount`, `role`, `evictable`, and `pluginSource`, but are open-ended. Plugin parents and their children, or system and tool-definition entries, are nested rollups: **do not blindly sum all entry rows as disjoint charges**. R:4375.

These token units are runtime-tokenized current-context measurements, with a model-dependent approximation—not provider-invoiced token charges. The contract explicitly describes one concrete `modelId` tokenization even for a session that used multiple Auto-selected models. Preserve `modelSource` (`autoResolved`, `selected`, `default`, or future values). The SDK wrapper does not expose the underlying tokenizer/attribution algorithm, so its exact fidelity was not independently validated. R:4375.

A skill entry occupying 2,000 tokens means 2,000 tokens are currently attributed to that skill in the window. It does not establish 2,000 tokens per invocation, 2,000 billable tokens, or a historical total. Compaction/eviction can reduce occupancy without undoing earlier usage. Summing snapshots would repeatedly count retained context. Likewise a plugin rollup can explain current resident contributions; it cannot allocate a request’s full input/output/reasoning bill to that plugin. Keep this view explicitly scoped to the hosting session and separate from date-filtered usage.

No stable public historical per-source attribution API was found in this installed SDK. Historical aggregate context samples, where independently persisted by the desktop, do not reconstruct these per-source snapshots. There is also no audited stable API that establishes the causal reason for a past cache miss; internal checkpoint/cache-state objects should not be treated as that contract.

## Compaction, plans, todos, and permissions

- **Compaction:** normally durable start/complete events expose shared `compactionAttemptId`, trigger, model/target, pre/post counts, category counts, limits, outcome/failure reason, and optional compaction-call tokens/duration. `tokenAccountingBasis` identifies trustworthy paired measurements; the current known value is `local_full_context_estimate`. Preserve missing counts and compare matching attempts/bases. The completion payload also contains summary/focus text and checkpoint paths: discard those for a metric view. `truncation` and `context_cleared` are distinct events, not interchangeable compactions. E:3512,4515,4565,4602,4647,4684,4817.
- **Compaction accounting:** its token reductions measure context occupancy removed, not money refunded. Optional `compactionTokensUsed` describes summarization work and may aggregate several calls. Do not add these values onto session receipts/totals until accounting identity and inclusion rules are verified. The [official observability guide](https://raw.githubusercontent.com/github/copilot-sdk/cf045793958ce674259c557f7769788f94ee20c9/docs/observability/opentelemetry.md) documents separate compaction spans, so trace counts also need deduplication against accounting.
- **Plans/todos:** `plan.read()` returns current file existence, contents and path. `readSqlTodos()` and `readSqlTodosWithDependencies()` return current rows (`id`, title/description/status/createdAt) and edges; absent storage/schema produces empty arrays. `session.plan_changed` is normally durable but reports an operation, while `session.todos_changed` is an **ephemeral invalidation** with no todo history. Current todo completion is not reliable historical throughput. Prefer counts/status only if added. R:24631,24652,24665,24694,24711,39772–39794; E:3287,3324,3333,3370.
- **Permissions:** normally durable request/completion pairs contain `requestId`, owner agent/session, permission kind/mode, decision source, outcome, and optional tool link. These can estimate approval/rejection counts and observed wait intervals when paired. Missing pairs, concurrent waits, automatic decisions, and hook decisions need separate treatment. Permission fact/path/prompt/risk payloads are sensitive; retain categories and IDs, not raw requests. `permissions.pendingRequests()`, `getMode()`, and `getCapabilities()` are reads; handling a pending request or modifying rules changes authority. E:11015,11052,12403,12440; R:41015,41037,41043.

## Keep observations separate from actions

The following is a proposed implementation boundary, based on declarations rather than live execution:

| Classification | Examples | Dashboard treatment |
| --- | --- | --- |
| Current snapshot reads | Context info/attribution/heaviest messages, usage totals, quota `get`, model/mode/current agent, tasks list, current initialized tool metadata, plugin inventory, MCP `listConfigured` | Candidates for a bounded reader on the existing joined session; null/unsupported/failure must preserve recorded usage. |
| Reads carrying content or substantial history | `getEvents`, event-log pages, plan read, instruction sources, invoked skills, task output | Not necessary for the first metadata-only insights. Bound and filter; avoid retaining content. |
| Reads that contact services or do extra work | `model.list`, `quota.refresh`, MCP `listTools`/resources/prompts/OAuth probe, re-tokenizing context, materializing built-in descriptors | Not equivalent to a cached passive snapshot. Do not use as an automatic fallback for absent metadata. |
| Initialization/reconciliation or consumed state | MCP `list` may start servers; tool `initializeAndValidate`; skills `ensureLoaded`; reload APIs; quota `takeWarnings`; event-interest registration | These can affect runtime behavior or consume host state. Keep outside ordinary dashboard collection. |
| Mutation or inference | `send`/`sendAndWait`, history compact/clear/truncate/rewind, task/fleet/workflow start, tool execution, MCP sampling/start/restart/authentication, plugin install/enable, model switches, instructions reload, permission decisions | Require a separate user-directed action. None should run just to explain efficiency. |

Relevant declarations: S:131–185; R:39984,39993,40004,40187,40196,40210,40240,40268,40320,40779,40815,40821,41009,41327,41375,41497,41523–41535. Treat `history.summarizeForHandoff()` as a potential generation path, not a passive snapshot: its contract produces a summary and does not promise zero inference. Existing OpenTelemetry client configuration is also an opt-in observability pipeline, not a historical-data query; no exporter/recorder was configured here.

## Practical order for an efficiency feature

1. Validate **current context attribution** through the existing joined-session reader in a separately authorized implementation. Keep the host session ID, observation time, model basis, null state, and parent/child structure. Start with aggregate categories and per-source occupancy, then optional body-free largest-message metadata.
2. Add **historical turn, agent, compaction and metered-tool metadata** only where the stored-data audit establishes coverage. Reuse accounting identities and preserve unknown outcomes/providers. Do not charge both detailed receipts and overlapping totals.
3. Use **current usage totals/quota/model context** as clearly labeled supplemental snapshots or reconciliation evidence. They cannot replace date-filtered receipt reports.
4. Defer **live transient-event recording** unless requested. Without a recorder, lost usage-info/model-failure/MCP-status events remain unavailable. An honest coverage gap is preferable to reconstructing it from unrelated signals.
5. Keep **memory quality, instruction adherence, usefulness, and time saved** outside automatic conclusions. The audited SDK supplies resource/activity evidence, not those outcomes.

Unverified: live success/authorization/null behavior of the newly identified methods; actual persisted coverage; tokenizer precision; accounting inclusion of special/compaction operations across runtime versions; desktop rendering. No inference about user history is made from the schemas alone.
