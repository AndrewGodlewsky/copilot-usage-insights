# Context, instructions, memory, and tool efficiency

See the [research index](README.md) for the expanded technique catalogue and the later stored-data/SDK audits, including current context attribution. This note preserves the earlier context and memory investigation; current context occupancy remains distinct from historical charges or evidence of usefulness.

Research checked 2026-11-14 for Copilot Usage Insights. This note proposes investigations, not diagnoses of the user's sessions. Its recommendation is to show a measured pattern, explain competing interpretations, and offer one controlled experiment. The current data does not establish task correctness, unnecessary work, or the cause of input growth: the parser retains accounting and activity metadata, while original prompt text is fetched separately for an explicitly expanded request. [Receipt parser](../../src/core/copilot.mjs), [prompt lookup](../../src/node/request-prompts.mjs), [request handler](../../src/node/canvas-server.mjs).

**Verified Copilot desktop capabilities.** GitHub's app-specific documentation confirms global app instructions, repository instructions, relevant skill loading, MCP servers, custom agents, and plugins. Repository or CLI skills and MCP configurations are available in the app. This establishes supported customization mechanisms, not whether a particular session loaded an instruction, memory, or tool schema. [Customizing the GitHub Copilot app](https://docs.github.com/en/copilot/how-tos/github-copilot-app/customize-github-copilot-app).

GitHub explicitly lists the app as a supported skills surface. Skills package instructions, scripts, and resources for particular workflows, and load relevant resources when needed. Personal and project skill locations differ by surface; use the applicable setup guide rather than assume every location works everywhere. [Agent skills](https://docs.github.com/en/copilot/concepts/customizations/agent-skills).

Shared **Copilot Memory** supports repository facts and user preferences. The app is listed, but availability depends on the account; policies and settings also control use. GitHub instructs Copilot to check repository memory citations against the current branch, but does not guarantee correctness. Durable requirements belong in custom instructions rather than a remembered fact that might not be selected. [About Copilot Memory](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-memory).

The app's **project Memory** is a separate set of project preferences remembered across tasks. Editing it does not edit shared Copilot Memory. Shared memories are managed through GitHub settings, and the app has no separate switch that grants account availability. Do not prescribe CLI memory flags or a CLI settings screen as app instructions. [Managing memory for your personal account](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/copilot-memory/manage-for-yourself).

**What the evidence supports.** GitHub recommends specific goals, requirements, examples, relevant context, and reviewing results; it also recommends a new conversation for a new task. Its guidance applies across surfaces, while attachment syntax and individual controls are surface-specific. This supports testing prompt completeness, not scoring a prompt by length. [Prompt engineering for GitHub Copilot](https://docs.github.com/en/copilot/concepts/prompting-and-context/prompt-engineering).

GitHub recommends concise, self-contained instructions and avoiding conflicting instructions. Supported instruction files and precedence vary by client and feature. A file named `AGENTS.md` existing on disk does not by itself prove the app loaded it or applied it to the request. Use the app's documented instruction settings for app experiments unless the relevant file mechanism has also been verified. [Custom instructions](https://docs.github.com/en/copilot/concepts/prompting-and-context/custom-instructions), [app settings](https://docs.github.com/en/copilot/how-tos/github-copilot-app/customize-github-copilot-app).

Anthropic describes just-in-time retrieval using paths and other references, targeted queries, and persistent notes. It also describes a tradeoff: runtime exploration can take longer than loading context beforehand, and overly aggressive compaction can discard useful detail. These are general agent design ideas and Claude examples, not proof that Copilot desktop implements the same algorithms. [Effective context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents).

Anthropic recommends clear tool boundaries, informative responses, filters, pagination, and useful errors; it evaluates task success alongside tool calls, tokens, errors, and time. Its claims about Claude's implementation or token limits must not be presented as Copilot desktop settings. [Writing effective tools](https://www.anthropic.com/research/writing-tools-for-agents).

**Repository instructions have mixed empirical results.** Gloaguen et al., revision 2, evaluated four model/agent configurations on 300 SWE-bench Lite tasks and 138 CTXbench tasks. Generated context files increased mean inference cost by 20% and 23% respectively without a significant resolution-rate improvement. Developer files improved CTXbench resolution by 2.4 percentage points on average, not significantly versus no file, while outperforming generated files. The work used Claude Code, Codex, and Qwen Code, not Copilot desktop. Its Python tasks, test-based success criterion, and single sampled completion per configuration limit generalization. This is evidence against treating generated repository overviews as a guaranteed optimization. [Paper, methods and results](https://arxiv.org/html/2602.11988v2#S4).

Lulla et al. compared paired Codex runs on 124 tasks from 10 repositories with and without a root `AGENTS.md`. They reported 28.64% lower median runtime and 16.58% lower output-token use with the file. The sample selected merged code-only PRs changing at most 100 lines and five files, used `gpt-5.2-codex`, and filtered for particular instruction content. Comprehensive semantic correctness was outside scope; a 50-task manual check established nontrivial output rather than full correctness equivalence. These narrower results do not establish that adding instructions improves quality-adjusted efficiency in this plugin's workloads. [Author-hosted paper, methods and limitations](https://assets.empirical-software.engineering/pdf/jaws26-agents.md-efficiency.pdf).

The practical research conclusion is a proposed decision rule: test a small, relevant instruction change against the same task with a fixed acceptance standard. Do not infer benefit from file presence, file length, or a lower token count alone.

**What the plugin can establish today.** Usage records include session/project, model, API call ID, initiator, duration, tokens, cache splits, reasoning, and recorded credits where available. Tool records retain names, server identity, timestamps, and an explicit success flag where available. Skill records retain names, source/version/path, timestamps, and user/agent/context-load/unknown triggers. Tool arguments, results, instruction content, memory content, compaction events, and task outcomes are not retained by the ordinary parser. These are current implementation facts, not claims about everything the underlying Copilot event format could contain. [Normalization and parser](../../src/core/copilot.mjs).

The reports aggregate calls and recorded outcomes, and omit activity whose provider attribution is unsuitable. Unknown outcomes remain unknown. Skills are counted as recorded loads, including context loads; counts do not measure usefulness. Prompt lookup follows `apiCallId` to a unique `interactionId` and user message, and may return unavailable. The request handler limits the displayed prompt to 12,000 characters. This is insufficient to reconstruct all instructions, retrieved content, or subsequent corrections that shaped an answer. [Activity reports](../../src/core/copilot-report.mjs), [prompt matching](../../src/node/request-prompts.mjs), [request handling](../../src/node/canvas-server.mjs).

One promising extension has an official source: the generated Copilot SDK event schema defines optional, internal `toolTokenCount` as tokens used by **tool definitions**, not tool results, and defines per-name `toolCounts`. The current parser does not retain them. These fields could strengthen metadata analysis after verifying event presence and semantics for the app versions being read; the SDK definition alone is not a desktop availability guarantee. They would not resolve scenario 3's missing result sizes. [GitHub SDK source](https://raw.githubusercontent.com/github/copilot-sdk/main/nodejs/src/generated/session-events.ts), [current parser](../../src/core/copilot.mjs).

**Concrete investigation scenarios.** Every observation below is conditional, not a finding that the pattern occurred. “Available” means the underlying metadata could support a descriptive calculation; some calculations would require new report logic. Hypotheses, confounders, and experiments are this note's proposals. The linked evidence motivates the experiment without proving its diagnosis.

| Scenario | Observable pattern and current limit | Hypothesis and competing explanation | Actionable experiment and required evidence |
| --- | --- | --- | --- |
| 1. Relearning repository navigation | Repeated early search/read tool names in the same project can be counted. The parser cannot identify files, queries, or whether this is the same task. | A missing entry point may cause rediscovery; unrelated files, branch changes, or careful orientation could explain it. | Test a short repository instruction naming the relevant entry point and authoritative test command. Compare matched tasks. Need task identity, repository revision, instruction-load evidence, and paths/queries to attribute any change. Navigation references are a general design technique. [Anthropic](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents). |
| 2. Reading the same unchanged content repeatedly | Several calls named `read` establish repeated tool use, not duplicate reads. | The agent might have lost a useful fact; the reads might cover different files, changed content, or separate agents. | Trial a concise progress note containing discoveries and next steps. Confirm duplicate work only with normalized target/range, content fingerprint, agent lineage, and intervening edits. Persistent notes motivate the experiment. [Anthropic](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents). |
| 3. Broad retrieval returns unnecessary material | Input growth after a tool-heavy interval is observable. Individual result size and relevance are not. | Large result sets may inflate context; useful source gathering or growing conversation history could produce the same pattern. | Compare a bounded search or filtered response with the existing workflow. Need result token/byte sizes, query scope, truncation markers, model-request linkage, and an equal-quality outcome check. [Tool response guidance](https://www.anthropic.com/research/writing-tools-for-agents). |
| 4. The first prompt omits a crucial requirement | Many user-started requests are visible; corrections and clarification questions cannot be distinguished from new work. An expanded original prompt provides only partial context. | The initial task may be incomplete; deliberate iteration or changing user preferences could explain the extra turns. | Trial a task brief containing objective, relevant files, constraints, expected result, and acceptance examples. Need full turn lineage, correction/clarification labels, and acceptance outcomes. Compare total task effort rather than first-prompt length. [Prompt guidance](https://docs.github.com/en/copilot/concepts/prompting-and-context/prompt-engineering). |
| 5. Repeatedly restating a stable convention | Session and request counts cannot detect semantic repetition. One inspected prompt may suggest a candidate, but cannot establish recurrence. | A durable instruction may be missing; the convention may instead be specific to one task. | Move one verified, broadly applicable convention into documented app or repository instructions. Need multiple prompt examples, instruction scope/version, evidence it loaded, and correction frequency before/after. [Instruction guidance](https://docs.github.com/en/copilot/concepts/prompting-and-context/custom-instructions). |
| 6. An instruction causes unrelated work | High tool counts or input sizes after an instruction change would be an association. The current index does not record that change or instruction loads. | A broad requirement might trigger irrelevant checks; tasks may simply have become harder or the check may prevent important defects. | Narrow one instruction's scope while preserving mandatory requirements. Need historical instruction content, task classification, linked tool intent, and regression outcomes. Benchmark findings motivate testing rather than automatic pruning. [Gloaguen et al.](https://arxiv.org/html/2602.11988v2#S4). |
| 7. Stale or conflicting repository instructions | Failure counts may reveal an investigation target. They cannot show a wrong command or instruction conflict. | An obsolete command or inconsistent rule might cause retries; a real code failure or environment outage is another explanation. | Validate one documented command against the current revision and resolve any verified conflict. Need active instruction sources, actual command/error, environment version, and repeat-run results. [Instruction guidance](https://docs.github.com/en/copilot/concepts/prompting-and-context/custom-instructions). |
| 8. A skill loads more broadly than needed | Repeated skill events and their triggers are available. `context-load` is not a manual invocation, and the current installed version may differ from the version used historically. | Discovery criteria might be too broad; the skill may be intentionally relevant to every task in the sample. | Review a sample of tasks, then trial a narrower description or explicit invocation for that workflow. Need historical skill contents, actual loaded resources, task labels, and outcomes. Skills are designed for relevant workflows. [Skills](https://docs.github.com/en/copilot/concepts/customizations/agent-skills), [version display](../../src/panel/panel.js). |
| 9. A useful reusable workflow is never selected | No recorded skill event establishes only no retained invocation in the selected data. It does not establish absence, lack of availability, or inefficiency. | A workflow may need clearer discovery metadata; it may be inapplicable or older sessions may lack the event. | For a recurring task, compare explicit skill invocation with the existing approach. Need availability/configuration history, event coverage, equivalent tasks, output checks, and total task usage. [Skills](https://docs.github.com/en/copilot/concepts/customizations/agent-skills), [parser](../../src/core/copilot.mjs). |
| 10. Durable project knowledge is rediscovered | Similar search-tool sequences across sessions can be counted. Neither memory availability nor memory retrieval is established. | A reusable fact may be missing; the fact may have changed, or validation may be appropriate. | Verify the account's shared Copilot Memory availability and inspect the separate project Memory setting. Trial one stable, reviewable fact or preference in the appropriate mechanism. Need retrieval evidence, fact provenance, branch state, and repeated-task outcomes. [Memory](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-memory), [app distinction](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/copilot-memory/manage-for-yourself). |
| 11. A remembered fact is stale | Repeated failures alone cannot identify a memory problem. A memory-related tool name would still not show which fact was supplied or relied on. | Stale context might misdirect the agent; the error may come from current instructions or code instead. | Inspect the cited fact against the current branch; correct the appropriate project preference or remove an unwanted shared memory. Need memory identity/content/citation, retrieval evidence, and the failing operation. Verification is not guaranteed by the memory mechanism. [Memory](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-memory). |
| 12. Testing repeats without useful changes | Repeated shell-tool names and outcomes are available; commands, tests selected, exit details, and code changes are not. | The same check might be repeated unnecessarily; tests after meaningful edits, flaky tests, or a requested final verification could justify repetition. | Trial a task-specific check plan after inspecting the trace. Need command fingerprints, test outcomes, code revisions between runs, and final regression coverage. Count useful completed work as well as resource use. [Tool evaluation guidance](https://www.anthropic.com/research/writing-tools-for-agents). |
| 13. Tool calls fail repeatedly | Explicit `success: false` is a recorded tool failure. Missing completion or success data is unknown. Neither reveals failure cause or task failure. | Bad parameters or unclear errors might drive retries; authentication, permissions, service downtime, and expected negative tests can also explain failures. | Inspect one failing tool and improve the diagnosed cause. Need error category, argument equivalence, retry reason, and completion outcome. Compare successful task effort after the change. [Parser](../../src/core/copilot.mjs), [error guidance](https://www.anthropic.com/research/writing-tools-for-agents). |
| 14. Overlapping tools create extra selection work | Current MCP/plugin inventory and observed calls show availability now and historical activity, not the exact schema set supplied to each request. | Similar tools might cause unnecessary switching; both might serve distinct required data or functions. | On one repeatable workflow, compare an appropriate reduced tool set with the original. Need per-request available-tool history, schema sizes, attempted operations, and equivalent outcomes before recommending removal. [Tool boundaries](https://www.anthropic.com/research/writing-tools-for-agents), [inventory/history merge](../../src/core/integrations.mjs). |

**A minimal evaluation proposal.** Record the task, repository revision, acceptance checks, model, app version, instruction/skill configuration, and relevant memory setting before the experiment. Change one factor. Repeat matched tasks sufficiently to see whether results vary; record unsuccessful attempts as well as accepted outputs. Report median and distribution of recorded credits, tokens, tool calls, errors, and time, together with acceptance and regressions. Treat unmatched historical comparisons as associations. This protocol is a design recommendation informed by the paired study methods and by tool evaluations that measure both completion and resources. [Lulla et al.](https://assets.empirical-software.engineering/pdf/jaws26-agents.md-efficiency.pdf), [Anthropic evaluation guidance](https://www.anthropic.com/research/writing-tools-for-agents).

For product wording, use “Several calls to this tool failed; inspect the errors” or “This skill loaded in many sessions; review whether its scope fits those tasks.” Reserve “duplicate,” “unnecessary,” “incomplete prompt,” “stale memory,” and “saved credits” for cases with the additional evidence named above. Proposed metadata additions are per-turn/agent linkage, tool durations and error categories, bounded result sizes, instruction/skill content fingerprints and load events, and task outcome labels. These are a future measurement design, not fields currently guaranteed by Copilot desktop or already collected by this plugin.
