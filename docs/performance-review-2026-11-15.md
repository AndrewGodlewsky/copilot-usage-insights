# Dashboard opening performance review

## v0.1.100: measured VS Code and WSL delays

The supplied v0.1.99 diagnostics identify a 30,005 ms initial usage load on the other Windows computer. History scanning took 28,689 ms: VS Code discovery/journals consumed 19,265 ms for 1,395 files (1,669,940,283 bytes); Copilot roots/journals took 3,078 ms; two WSL databases then took 2,192 and 3,615 ms sequentially. Report calculation took 1,193 ms, response decoding 5 ms, and DOM work 50 ms. Inventory was separate. These measurements identify source reading as the primary delay; they do not identify antivirus, drive speed or an individual file as the cause.

VS Code was awaiting each journal before beginning the next. It now reads up to eight journals concurrently using the existing bounded queue pattern. Discovery order, CLI precedence, copied-log ownership, parser limits, incremental caching and source warnings are preserved. Two usage databases may read concurrently; their results are still applied in source order. For recognized WSL database paths on Windows, the local SQLite probe no longer waits one second for a lock before using the existing native WSL fallback. Local Windows databases retain their lock wait; WSL opt-out, read-only transactions, deadlines, and the check that the distribution is already running remain unchanged.

The reproducible synthetic benchmark is:

```text
node scripts/benchmark-vscode.mjs --files=1395 --kib=1168
```

It creates 1,395 synthetic journals across 40 workspaces (1,668,745,320 bytes), verifies exact credits/record counts and unchanged-snapshot reuse, runs three fresh scanner instances, then removes only its verified temporary fixture folder. It reads no personal logs. On the development Windows machine:

| Measure | v0.1.99 | v0.1.100 |
| --- | ---: | ---: |
| Fresh scanner, three runs | 4,585 / 4,943 / 4,741 ms | 3,385 / 3,235 / 2,942 ms |
| Fresh scanner median | 4,741 ms | 3,235 ms |
| Unchanged scan median | 173 ms | 130 ms |

The initial median improved about 32% in this fixture. Operating-system caches were warm after fixture creation. This synthetic shape has one accounting event with a large payload per file; actual histories have different event shapes. It does not reproduce the other computer's storage, real WSL process startup or browser paint, and does not predict its final load time. Tests separately exercise overlapping delayed reads, ordered duplicate reconciliation, per-source failures, WSL fallback/opt-out, committed WAL data, and zero-credit accounting. No history is skipped by date, no persistent usage cache is added, and the remaining full-history parsing cost still grows with bytes and events.

After updating, reopen the dashboard and use **Show logs → Download logs (.md)** after the initial load, before Refresh. The Markdown contains the same sanitized snapshot as Copy logs, with the existing stage timings. Confirm the actual download in the desktop host and compare the affected computer's new timings; neither has been verified through desktop/browser automation.

## v0.1.99: startup diagnostics and scale check

The other computer's slow opening has not been reproduced locally. This release makes the existing scan observable rather than changing accounting or skipping older history. Existing logs timed the entire scan, report, skill versions and rendering, but did not separate the work inside the scan. The report cache-hit field was also being dropped by the diagnostic allowlist; it is now reported as `cacheHit`.

Measured on the development Windows machine, with synthetic histories generated by `benchmark-performance.mjs --scale`. These are cold scanner/parser caches; operating-system file caches may be warm. They exclude Copilot startup, WSL/network storage, real SQLite databases and browser paint. Different payloads below are separate scenarios, not a linear scaling comparison.

| Scenario | Journals / empty folders | Journal size | First scan | First all-history calculation | First 7-day HTTP response | Unchanged scan |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 10,040 requests, realistic payloads | 328 / 500 | 357.1 MiB | 766 ms | 118 ms | 808 ms | 14 ms |
| 50,011 requests, compact payloads | 1,617 / 2,000 | 299.2 MiB | 2,234 ms | 509 ms | 2,630 ms | 85 ms |

The first scan dominated these local runs. Many session directories add filesystem work even without usage; long journals add read/parse work. Prompt attribution, deduplication and report aggregation also grow with retained metadata, not simply the number of visible columns. The first scan covers enabled history before date filtering so copied logs, cross-date prompt chains, historical calendar data and fallback accounting remain correct. Existing incremental and report caches make later loads much cheaper.

Three alternating scans of the same 50k fixture measured 1,855/1,628/1,631 ms without diagnostics and 1,712/1,668/1,653 ms with the rotating runtime log enabled. The medians differ by 37 ms (about 2%); this small sample includes filesystem/GC noise and is not a universal overhead guarantee. One instrumented run attributed 1,632 ms to journals, 13 ms to deduplication and 5 ms to final reconciliation. No extra history reads are performed for these measurements; counters update per file or byte chunk, not per event log entry.

**Show logs → Copy logs** now includes a readable timing summary followed by structured events:

- `ui.load`: initial/manual/automatic/filter loading through the DOM update, including failed attempts.
- `history.discovery`: WSL discovery; `history.copilot`: root probing and all Copilot journals; `history.journals`: an individual anonymous source, including session folder/name metadata.
- `history.vscode`: VS Code discovery and journals across enabled roots.
- `history.merge`: journal deduplication and cache reuse; `history.database`: each usage database, including native WSL fallback when used; `history.names`: desktop session names; `history.finalize`: coverage and snapshot reconciliation (includes names).
- `report.build`, `skills.versions`, `report.serialize`: calculations, installed versions, JSON/fingerprint preparation and response byte count.
- `api.decode`, `ui.render`: response body download/decoding and JavaScript/DOM work; inventory remains independently timed.

`filesRead` counts full journal reads begun, `filesAppended` counts append reads begun, and `filesReused` counts unchanged journals. `bytesRead` counts journal bytes read for parsing; `bytesHashed` counts additional prefix validation reads. Metadata/database bytes are not included. Logs retain counts and storage categories, never source names, paths or prompt text. Source and report stages are also written to the existing bounded runtime log so an interrupted load can leave a started-stage record. Starts without completions can also reflect in-flight work or dropped log entries; they are not classified as failures.

On the affected machine, reopen the updated plugin, let the initial load finish or fail, and copy logs **before Refresh**. If the server is unreachable, the existing saved-log import remains available. Timings may nest and come from different loads; each summary row has its own timestamp. This does not measure the time before the dashboard script starts, browser paint, or identify a slow individual file within a source. Those are follow-up measurements if the new stages point there.

## Earlier v0.1.70 review

The dashboard waited for live plugin/MCP inventory before displaying usage, even though the usage report did not depend on it. Version 0.1.70 separates those operations. It also reuses number formatters and avoids generating hidden Overview/Cache detail views.

The latest Efficiency content added measurable rendering work, but local measurements did not reproduce a multi-second regression from that change alone. The inventory dependency and repeated formatter construction existed before 0.1.69. Actual Copilot canvas startup and browser paint were not measured; no browser or desktop automation was used.

## Changes and safeguards

- `usage.report` returns usage and historical MCP calls without waiting for live inventory. `usage.inventory` reads passive host metadata separately; it makes no model request.
- Pending inventory cannot hide usage or keep Refresh disabled. Loading and unavailable states are scoped to inventory. Explicit/automatic refresh requests queue one follow-up inventory read if needed; filter changes do not add host reads.
- Late inventory results merge into the latest filtered history. They do not overwrite current filters or add duplicate MCP call counts. Open details and keyboard focus survive updates; a removed server returns focus to MCP sorting.
- Locale formatter instances are cached by options, with a maximum of 32 entries. Small nonzero credit precision and full/simplified formatting retain their existing behavior.
- Dedicated token Overview/Cache detail markup is generated when that section is selected, then refreshed when visible. Section selection and explicit context inspection behavior remain unchanged.
- No database, additional log source, paid AI call, or persistent usage cache was introduced. Accounting and attribution calculations are unchanged.

## Wider sweep and remaining costs

| Area | Finding / next step if measured slow |
| --- | --- |
| First history scan | Reads all enabled logs before filtering. A safe date index would need to handle copied logs, corrections, spanning sessions, and incomplete prompt chains. Keep correctness; use `history.scan` timing to justify a separate indexing change. |
| Incremental scans | Reuse parsed records for unchanged logs. Appended-file prefix validation still reads previous bytes to detect rewrites. Removing that validation could silently miscount corrected history. |
| Prompt attribution and report grouping | A synthetic CPU profile identified prompt-credit grouping as a leading cost. It intentionally groups before date/model filters. The current implementation caches attribution by snapshot and session, with invalidation for changed events, completions and parent links. |
| Session names / source settings | Read current metadata so renames and enabled-home changes take effect. Do not indefinitely cache these for a small speed gain. |
| Installed skill versions | Current skill versions still block the report; reads are now concurrent by unique path with size/timestamp caching. Local time was 2.4 ms. Many skills or remote paths may cost more; inspect `skills.versions` before introducing concurrency or caching. |
| Other hidden UI | Some top-level panels still render on report changes. Formatter reuse reduces this cost; broader lazy rendering would require focus/refresh coverage across all tabs. Only the newly duplicated token details were changed here. |
| Prompt details | Local prompt text is read only when a user expands a request. It is not part of opening the dashboard. |
| AI Review / context inspection | AI runtime, authentication/catalog work, and model calls remain explicit actions. Context inspection is also explicit. Neither runs automatically on dashboard startup. |
| Refresh | Automatic refresh is now every 15 minutes while visible, with a staleness check on returning to the page. Explicit Refresh intentionally forces a reread. |
| Host and paint | Copilot canvas startup, SDK host latency, browser layout, and paint need an actual manual run. Server/VM timing does not capture them. |

## Reproducing measurements

From the repository root, using its supported Node version:

```text
node scripts/benchmark-performance.mjs
node scripts/benchmark-performance.mjs --startup
node scripts/benchmark-performance.mjs --format
node scripts/benchmark-performance.mjs --local
```

The default synthetic fixture uses real parser/report code at 1,000, 5,000, and 10,000 records, with all-history, Today, 7-day, and model-filtered reports. Each prompt has one complete charged model call; this is a repeatable comparison, not a simulation of every real history shape. `--startup` injects a one-second inventory delay into the real local HTTP server. `--format` renders 20,000 numeric values. Add `--repo=<absolute checkout path>` to compare another compatible checkout using the same script.

Only `--local` reads personal usage sources. It respects enabled/disabled homes and optional SDK receipt directories, and prints counts/timings without names, paths, IDs, or prompt content. Run repeated samples and compare the same history and machine; filesystem cache, warm-up, and other workloads affect results.

Regression coverage includes slow inventory, filter changes during a pending read, coalesced refreshes, inventory failure, focus restoration, deferred token details, formatter reuse, and existing accounting tests. Release validation requires `npm run build` and `npm test`.

If opening still feels slow, manually reopen the updated plugin and copy **Show logs** while it is still open. Compare `history.scan`, `report.build`, `skills.versions`, `inventory.read`, `api.request`, and `ui.render`. A slow inventory should now affect only live inventory availability. A delay before `ui.started` cannot be diagnosed from the dashboard's own timestamps.
